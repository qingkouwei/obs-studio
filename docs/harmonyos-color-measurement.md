# 色准测量报告（B3 前置）——双重编码根因实锤与修复路线

> 日期：2026-10-02。设备：MatePad Edge（PC/2in1，HarmonyOS 7.0.0.109 / API 26，Maleoon 916B）。
> 方法：mac 局域网 HTTP 服务一张 16-patch sRGB 色卡页（8-bit 精确值，无 dither），
> 设备浏览器全屏显示；基线 = `snapshot_display` 抓屏（系统合成器输出，恒等路径）；
> 被测 = OBS 屏幕采集 → 录制 → 成片抽帧。两路取同坐标像素对比。

## 一、基线：显示链路无损

| patch | 期望 | 屏幕实拍 |
|---|---|---|
| 全部 16 个 | 0/16/26/64/96/128/160/192/224/255 及原色 | **逐项精确命中（灰阶 delta=0，原色 delta≤2）** |

结论：浏览器→合成器→屏幕→抓屏是恒等路径，测量可信。

## 二、OBS 录制链路：灰阶系统性变暗，原色无恙

| patch | 期望 | 录制片段 | 期望的 sRGB→linear→sRGB（双重编码预测值） |
|---|---|---|---|
| 16 | 16 | **0** | 0.6 → 0 ✓ |
| 26 | 26 | **2** | 2.3 → 2 ✓ |
| 64 | 64 | **11** | 10.9 → 11 ✓ |
| 96 | 96 | **28** | 27.6 → 28 ✓ |
| 128 | 128 | **54** | 54.7 → 55 ✓（±1） |
| 160 | 160 | **89** | 90.6 → 91 ✓（±2） |
| 192 | 192 | **132** | 133.0 → 133 ✓ |
| 224 | 224 | **188** | 188.9 → 189 ✓ |
| 原色 6 个 | 0/255 端点 | **±2 内** | 端点恒等（0→0、255→255）✓ |

**八个非端点灰阶全部命中"解码一次"曲线，无一例外；饱和原色因端点不动而幸免。**

## 三、根因判定

输出 = 输入经 sRGB EOTF 解码（linearize）后的值，即**整条链路做了一次解码、缺了最终编码**。

机制：libobs 的 sRGB canvas（`GS_CS_SRGB`）在 D311/Metal 上由 **sRGB 格式渲染目标在写入时自动做 linear→sRGB 编码**；
OHOS 上因 Maleoon 驱动拒绝 `(GL_SRGB8_ALPHA8, GL_BGRA, UNSIGNED_BYTE)` 三元组（journey §3.4），
GS_BGRA 退让为 `GL_RGBA8`（gl-subsystem.h 注释明示）——**采集输入的解码还在（shader 显式 srgb→linear），
输出的编码没了（RT 不再自动 encode）**。观感"大体正常"是因为端点恒等 + 人眼对暗部压缩不敏感，
但中间调整体压暗一档（128→54 已属肉眼可见）。

## 四、修复路线（三选一评估）

| 路线 | 做法 | 评估 |
|---|---|---|
| A. sRGB FBO | `glFramebufferTexture2D` 挂 `GL_SRGB8_ALPHA8` 纹理，靠驱动写入自动编码 | **首选试验**：Maleoon 对纯 RGBA 的 SRGB8_ALPHA8 组合未必拒（被拒的是 BGRA 三元组）；改动最小、语义与桌面完全一致 |
| B. shader 端编码 | 最终输出 pass 追加 linear→sRGB | 正确但侵入 libobs 渲染链（要区分目标是否 sRGB-aware），维护成本高 |
| C. 采集端不解码 | 输入跳过 srgb→linear，全链路"假 sRGB"直通 | 会破坏滤镜数学（色彩校正在非线性域计算），否决 |

**决策**：先试 A（一次真机实验定生死）；A 不成再评估 B。

## 六、路线 A 实验结果（10-02 晚）——**修复生效**

实现：`gl-texture2d.c` 中 GS_BGRA 且 `GS_RENDER_TARGET` 时 internal format 用 `GL_SRGB8_ALPHA8`
（被 Maleoon 拒的是 BGRA_EXT 三元组，RGBA/UNSIGNED_BYTE 组合是 ES3.0-core 被接受）；
可采样源纹理保持线性 GL_RGBA8（其解码在 shader 里显式做）。

验证（重启设备清坏态后，录制最大化 OBS 界面，与系统截图同坐标对比）：

| UI 元素 | 截图（恒等） | 修复后录制 | maxΔ | 修复前预测 |
|---|---|---|---|---|
| 场景选中蓝条 | (63,127,255) | (63,123,253) | 4 | ~压暗一档 |
| 混音条深蓝 | (14,16,19) | (13,15,20) | 1 | ~压暗一档 |
| 面板底色 | (37,38,44) | (37,35,42) | 4 | ~压暗一档 |
| 来源按钮浅灰 | (228,229,235) | (210,211,217) | 18* | — |

*浅灰处偏差含 h264 色度 4:2:0 采样与缩放取整噪声；关键是非端点灰不再落在 EOTF 曲线上。
**结论：双重编码消除，色准路线 A 关闭。**

## 七、附带发现的独立遗留（非本次改动引入）

反复"采集会话启停 + 应用焦点切换"后应用会 ANR（THREAD_BLOCK_6S）、录制文件 0 字节——
sRGB 改动**之前**的构建同样复现（17:45 那轮窗口 Picker 测试即已出现），属 §3.13 家族的
设备侧采集/图形坏态，需专项排查（怀疑 AVScreenCapture 会话快速销毁重建时驱动侧资源回收路径）。
规避：测量类操作前重启设备，单轮会话完成全部抓取。

## 五、复现脚本要点

- 色卡页：`/tmp/colorcard/index.html`（4×4 grid，16 patch，`100vw/100vh` 无 margin）
- 服务：`python3 -m http.server 8000 --bind 0.0.0.0`（mac 192.168.0.100）
- 打开：`aa start -b com.huawei.hmos.browser -a MainAbility -U "http://…"`
- 录制流程：OBS 前台 → 点"开始录制" → `aa start` 浏览器 → 停留 → `aa start` OBS → 停止
- 采样坐标：屏幕 3120×2080，内容区 y∈[7.5%, 94.5%]，4×4 网格中心；视频 1920×1080 按 sx=1920/3120 缩放
